= Artefact State Record — v0 Specification
:toc:
:toclevels: 3

[NOTE]
====
*PROVISIONAL — v0.* This is `stateful-artefacts`' own canonical deliverable: a
small, machine-readable *state record* that any estate artefact (binary,
container, dataset, document) can carry. The four top-level fields
(identity, provenance, lifecycle phase, verification status) are fixed by the
project's stated purpose (README/EXPLAINME/STATE/ECOSYSTEM/Intentfile). The
*sub-fields and serialization* below are v0 and may be refined when the
domain content is re-transferred from `hyperpolymath/reposystem`. Evolution is
*additive-only* (see <<Compatibility>>).
====

== Purpose

An artefact state record answers, in one self-describing unit: _what is this
artefact, where did it come from, where is it in its lifecycle, and has it been
verified?_ Producers such as Reposystem or CI can attach a record to an
artefact. Potential consumers include vordr, cerro-torre, and svalinn; no live
consumer integration is claimed here, and VeriSimDB mapping is out of scope.
This spec defines
the v0 record and its two state machines. The Idris2 sources model the
intended C-ABI layout, and the record is exposed through the
`stateful_artefacts_*` C ABI; those layout-proof sources are not yet
machine-checked by this repository's CI.

== Terminology for modular modality groups

Use *modality profile* as the number-agnostic term for the modalities selected
or supported by a particular database implementation or deployment. A profile
identifies membership and any required/optional status; its cardinality is
implementation-specific. The *modality set* is the membership itself.

* *Octad* names the current upstream VeriSimDB contract/model with eight
  modalities. Use it when referring to that specific upstream shape.
* *Hexad* ordinarily denotes six members; legacy project identifiers may use
  the word for other shapes. It is not a generic name for a configurable
  modality group, and its use does not establish the current API cardinality.
* This terminology does not assert that the current Octad API accepts arbitrary
  subsets or variable cardinalities. That is determined by its versioned
  upstream contract; this repository has no mapping or serialized profile
  contract of its own.

== Record shape (v0)

[cols="1,1,3",options="header"]
|===
| Field | Type | Meaning

| `schema-version` | u32 | Record schema version. v0 = `1`.
| `identity.id` | string (≤255) | Stable identifier for the artefact.
| `identity.kind` | enum `Kind` | `binary` \| `container` \| `dataset` \| `document` \| `other`.
| `provenance.source-ref` | string (≤255) | Where it came from (e.g. `repo://…`, a URL).
| `provenance.produced-by` | string (≤255) | The tool/agent that produced it.
| `provenance.timestamp` | i64 | Unix seconds; `0` = unset.
| `provenance.signature-ref` | string (≤255, optional) | Detached-signature locator; empty = none.
| `phase` | enum `Phase` | Lifecycle position (see <<Lifecycle>>).
| `verification` | enum `Verification` | `unverified` \| `verified` \| `rejected`.
| `verification.evidence-ref` | string (≤255, optional) | Locator for verification evidence; empty = none.
|===

Enum numeric codes (stable; shared by the C header and the Idris2 model):
`Kind` binary=0, container=1, dataset=2, document=3, other=4 ·
`Phase` draft=0, built=1, released=2, superseded=3, withdrawn=4 ·
`Verification` unverified=0, verified=1, rejected=2.

[[Lifecycle]]
== Lifecycle state machine (`phase`)

Phase only ever moves *forward*; there is no silent regression.

----
draft ──▶ built ──▶ released ──▶ superseded
  │         │          │
  └────────┴──────────┴──────────▶ withdrawn        (terminal)
superseded, withdrawn: terminal (no outgoing edges)
----

Legal transitions (everything else is rejected with `invalid_param`):

* `draft → built`, `draft → withdrawn`
* `built → released`, `built → withdrawn`
* `released → superseded`, `released → withdrawn`
* `superseded`, `withdrawn` — terminal.

== Verification state machine (`verification`)

The governing invariant is *verification-monotonicity*: a record never
*silently* loses a verification verdict. Moving away from `verified`/`rejected`
back to `unverified` is possible only through an explicit *reopen* operation.

* `set-verification(verified|rejected)` — allowed from `unverified`, and between
  `verified`↔`rejected` (evidence changed). Setting `unverified` this way is
  refused (`invalid_param`).
* `reopen()` — the *only* path back to `unverified`; models a deliberate
  re-assessment.

== Serialization (v0)

The v0 text serialization is a deterministic, line-oriented `key=value` form,
one field per line, in the field order of the table above. Optional fields with
empty values are omitted. The current Zig writer inserts string bytes as-is; it
does not define escaping for newlines, delimiters, or invalid UTF-8. Because the
format remains PROVISIONAL and has no agreed parser/consumer contract, do not
rely on it for untrusted strings until encoding/validation rules and tests are
specified. Example:

----
schema-version=1
id=repo://hyperpolymath/stateful-artefacts@dbca601
kind=0
source-ref=github://hyperpolymath/stateful-artefacts
produced-by=ci/e2e
timestamp=1751500000
phase=1
verification=0
----

The `src/bridges/verisimdb-feed.sh` output is *not* this normative text
serialization. It is a separate, PROVISIONAL local JSON envelope containing a
subset of v0 fields for safety testing; no downstream contract has been agreed.
Do not treat that JSON shape as a frozen record format or as a VeriSimDB API
payload.

[[Compatibility]]
== Compatibility rule (additive-only)

* New fields are *appended*; existing keys keep their meaning and numeric codes.
* Readers *ignore unknown keys* (forward-compatible) and *tolerate missing
  optional keys* (backward-compatible).
* Removing or renumbering a field, or narrowing an enum, is a *breaking* change
  that bumps `schema-version`.

This rule is modeled by the `additive-schema` /
`backward-readability` invariant in
`verification/proofs/tlaplus/ArtefactLifecycle.tla`. That TLA+ source has not
been machine-checked by the current repository CI.

== Out of scope for v0 (do not assume)

* An adapter mapping from this v0 record to VeriSimDB. The current upstream
  (`hyperpolymath/verisimdb`) documents an eight-modality *Octad* JSON API; this
  repository has not found a versioned upstream six-field `hexad` feed contract.
  Nor has it agreed how the v0 record maps into the current API. `src/bridges/`
  is a tested, local-only provisional JSON serializer, not an adapter, sink, or
  canonical record serialization. See
  the upstream
  link:https://github.com/hyperpolymath/verisimdb/blob/main/connectors/shared/json-schema/octad-input.json[Octad input schema]
  and link:https://github.com/hyperpolymath/verisimdb/blob/main/connectors/shared/openapi/verisim-api-v1.yaml[API specification].
* Reposystem's domain semantics (yard/track/switch-point records, graph-export
  and scenario-state schemas) — those arrive with the re-transfer.
